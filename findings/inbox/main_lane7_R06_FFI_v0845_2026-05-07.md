**FNV-1a spec validation:**
- The empty-string hash matches the FNV-1a 64-bit `offset_basis`
  `0xcbf29ce484222325` reinterpreted as signed i64 (which is
  `-3750763034362895579`). This is the spec'd value and confirms
  the Rust bridge's FNV-1a implementation matches.
- `null-byte` (`"\0"`) matches `empty` because Nucleor's string
  literal is passed to the Rust bridge as a C-string and the C
  ABI truncates at the first null. This is a documented FFI
  boundary behavior, NOT a hash bug. Cross-platform parity is
  preserved (both Windows and Linux truncate identically).

## Q7B: direct_ffi allowance enforcement audit

### Current state

The compiler's RFC-0062 G-9 Phase 2a banner (info[FFI-G125] family
in s1) declares the surface:

> Per RFC-0062 G-9 Phase 2a: direct `extern fn` calls bypass the
> safe-code bounds-check insertion that wraps Nucleor index/range
> operations. Adopter discipline today: treat every `extern fn`
> call site as an unsafe surface. Phase 2b will require
> `#[allow(direct_ffi)]` on the calling fn or `unsafe { }` block;
> Phase 4 promotes to hard error if missing.

Today the banner counts `extern fn` declarations in the resolved
source and surfaces the count via the audit info. There is NO
per-call-site enforcement that the calling fn carries
`#[allow(direct_ffi)]`. The audit has done its job; Phase 2b is
the next ship.

### How direct FFI calls are represented in s1

- `extern fn nuc_foo(args...) -> ret` — module-level declaration
  rewritten by the compiler driver into a forward `declare`
  emission in the LLVM IR. No allocation, no bounds check, no
  ownership tracking.
- Call site: a regular fn-call AST node where the callee resolves
  to an `extern fn` declaration. The IR emit lowers it as a
  `call` to the declared symbol — same shape as a Nucleor user
  fn call from the type-checker's perspective.
- The type-checker's TYP-005 "undefined function" check treats
  `extern fn` as defined and lets it through (line 22816 area
  comment: "will fail at clang link if not a privatized
  cross-module fn"). FFI-aware visibility is NOT enforced.

### Smallest v1.0-safe fail-closed rule

Two options, in order of cost:

**Tier A — banner-level audit (no code change, ~5 LOC banner):**
The existing FFI-G125 banner already counts `extern fn`
declarations. Extend it to count call sites whose calling fn does
NOT carry `#[allow(direct_ffi)]`, and surface the unprotected-
call-site count. Adopters get visibility without forcing a parser
change. ~5 LOC at the banner emission site, no fixture changes.

**Tier B — source-text per-call-site warning (~30-50 LOC + 2 fixtures):**
Add `enforce_direct_ffi_allowance(diags, source)` that:
1. Walks the resolved source for `extern fn <name>(...)` patterns
   and records the names in `extern_fn_set`.
2. For each fn whose body contains `<name>(` substring for any
   `<name>` in `extern_fn_set` AND whose header lacks
   `#[allow(direct_ffi)]`, emit `warning[FFI-002]` at the call site.
3. Adopters who actually need direct FFI add the attribute and
   the warning suppresses (existing `filter_allow_suppressed` path
   handles it).

Tier B keeps the warning-level diagnostic friendly to existing
code, requires zero stdlib changes (every existing `extern fn`
caller would need the attribute, OR they accept the warning).
Phase 4 promotes to error.

**Defer to Phase 4 — full AST-level enforcement:**
The canonical RFC-0062 Phase 2b requires AST-level call-site
walk, not source-text. Source-text is right for v1.0 audit; AST
is right for cert-mode hard error.

### Recommendation

Ship **Tier A** for v1.0 (banner extension only — discloses the
gap without forcing adopter discipline change). Tier B + Phase 4
remain post-v1.0. Total v1.0 lift: ~5 LOC.

## Q7C: concurrent rust_bridge stress

### Goal

Per handoff: opt-in stress for concurrent string return/free
behavior. Keep out of default verify if slow or environment-
sensitive.

### Current state

The R06 audit (Cloud_Control1.md §8C residuals) reports:

> POSIX rust_bridge ownership proof on native Linux (passed). 70k
> alloc/free cycles through rust_free_str. Valgrind evidence shows
> no definite/indirect leaks for targeted fixtures.

So the SINGLE-THREADED ownership contract is solid. Concurrent
stress would touch:
- Same `rust_to_uppercase` / `rust_base64_encode` / etc.
  Rust-owned-string returns from N concurrent Nucleor threads.
- Each thread holds + frees its own string handle via
  `rust_free_str`.
- Verify no cross-thread aliasing or double-free.

### Smallest v1.0-safe scaffold

A new fixture `tests/features/rust_bridge_concurrent_stress_smoke.nr`
gated behind `NUCLEOR_R06_STRESS=1` (env-var opt-in, NOT in
default verify). Body:

```nucleor
import "stdlib/rods/rust.nr"
import "stdlib/rods/threads.nr"  // if reliable on Windows + Linux

fn worker_uppercase(iter_count: i64) -> i64 {
    let mut i: i64 = 0;
    while i < iter_count {
        let s: str = rust_to_uppercase("nucleor-r06-stress");
        // Cheap correctness check + free.
        if str_eq(s, "NUCLEOR-R06-STRESS") != 1 {
            rust_free_str(s);
            return 1;
        };
        rust_free_str(s);
        i = i + 1;
    };
    return 0;
}

fn main() -> i32 {
    if env_get("NUCLEOR_R06_STRESS") != "1" { return 0; };  // skip
    let n_threads: i64 = 8;
    let iters_per: i64 = 1000;
    // ... thread spawn + join logic ...
    return 0;
}
```

### Why it's deferred

The threads/spawn rod's cross-platform behavior (Windows pthreads
emulation vs POSIX native, plus the `nucleor_random_*` POSIX
bridges shipped in cloud's R2 fix) needs at least one full pass
through verify.sh on the merged main before this fixture is
trustworthy. Cloud's Round-3 §8J full verify came back 1266 PASS /
0 FAIL on the post-R1-R5 main — that's the foundation; the
stress fixture is the next layer.

Recommendation: defer to a separate fix branch
(`fix/r06-rust-bridge-concurrent-stress-v0845` recommended) that
spools up after the post-Lane-2/3/4/5 main has been re-validated
on Linux. This branch ships the design, not the fixture.

## Honest residuals

1. **Q7A null-byte parity.** Both platforms hash `"\0"` same as
   `""` because of C-string truncation at the FFI boundary. Not
   a bug, but worth surfacing in the fixture comment.
2. **Q7A escape-sequence coverage.** Nucleor's recognized-escape
   set today is `\n\t\"\\r\0\\\\\\'`. Higher-bit-pattern bytes
   (`\xNN` etc.) are not yet supported (NR025 fail-closed). The
   transcript uses ASCII inputs only.
3. **Q7B Tier A counter accuracy.** Counting un-allowed FFI call
   sites at the source-text level is heuristic — same-name fns
   in adopter code that aren't actually `extern fn` get counted
   too. Tier B's pre-pass against `extern_fn_set` fixes this;
   Tier A audits, Tier B enforces.
4. **Q7C threads-rod readiness.** Pre-condition; no fixture in
   this branch.
