## Honest residuals

1. The new `UnitAcceleration` normalizes to canonical (m, s) inside `unit_acceleration_from_velocity_time` for downstream simplicity. An alternative API would carry through the source (distance, time) units; this design choice was made for predictability and parallels how the existing `UnitVelocity` exposes `unit_velocity_value_mps` as the canonical view.
2. `UnitTemperature` was deliberately deferred. The existing `unit_convert_f64` is linear (`val * scale`) and would silently miscompute Celsius<->Fahrenheit which is affine. Adding `UnitTemperature` would either require an affine-aware conversion path (broader rod change) or a fail-closed `panic` on temperature conversion through this surface (poor UX). Out of 6C scope.
3. The handoff said "if they preserve the current zero-surprise contract." The contract preserved here is: nominal storage, explicit conversion via `*_value_as`, no implicit cross-dimension coercion, dim-vector identity via `dim_*()`. The new helpers obey that contract.
4. No new `dim_*` constants were added — `dim_acceleration`, `dim_kg`, `dim_s` already existed. New code reuses the existing dim substrate.
5. Did not extend the `unit_dim_audit_smoke.nr` fixture to cross-check the new structs' dimension vectors. Per honest-residuals, extending the audit is a small follow-up; the per-struct positive smokes already lock `dim_eq(unit_X_dim(), dim_X())`.
