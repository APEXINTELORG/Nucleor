## Integration Gate Checklist

The gates below must ALL be green before `Nucleor_OSS` accepts a `nuc port` shim referencing Translate. Each gate names a verifiable check; an integration owner closes the gate by attaching evidence (artifact path + SHA or transcript) to the integration record.

### G1 — Translate working-tree state

- **G1.1** Clean tree at the integration ref: `git -C <translate-checkout> status --short --branch` reports zero modified, zero untracked files (or all untracked are explicitly ignored by `.gitignore`).
- **G1.2** Pinned tag exists: integration ref is a signed or annotated tag (e.g. `spec-12-complete`, not just a branch HEAD).
- **G1.3** Pinned Nucleor compiler version: Translate's pinned snapshot (`docs/PROGRESS.md` "Pinned snapshot: Nucleor X.Y.Z" + `tools/refresh-nucleor-ref.{ps1,sh}`) matches the `Nucleor_OSS` release the shim ships against. **Current drift, not yet closed:** `docs/PROGRESS.md` says 0.4.5; local wrapper reports 0.4.11.
- **G1.4** No vendored Nucleor compiler binary: Translate must build against a `Nucleor_OSS`-published compiler artifact, not a vendored copy whose provenance is unverifiable.

### G2 — Verify gate

- **G2.1** `bash tools/verify.sh` green from a clean checkout on Linux. Transcript captured. Evidence: full transcript artifact under `findings/inbox/translate_integration_<id>_v0845.md`.
- **G2.2** `pwsh tools/verify.ps1` (or its current Windows equivalent) green from a clean checkout on Windows. Transcript captured.
- **G2.3** Test footprint matches the documented count (most recently 368 PASS) and the count is asserted by the gate, not by hand.
- **G2.4** Verify-gate output passes a deterministic SHA check: a second clean run on a fresh worktree produces byte-identical PASS lines.
- **G2.5** Per-frontend smoke fixtures pass: at least one E2E fixture per supported frontend (`c, go, javascript, python, rust, typescript`) is exercised by `verify.sh` and the count is asserted.

### G3 — License and legal

- **G3.1** Translate `LICENSE` is Apache-2.0 (already verified). Any sub-component licensing is enumerated in `Nucleor.toml`/`nuctranslate.toml` provenance fields.
- **G3.2** No GPL/AGPL transitive dependency reaches the artifact `nuc port` would invoke (license SBOM scan from G6 confirms).
- **G3.3** All third-party tooling Translate invokes (`syn` for Rust, TS Compiler API JSON bridge, clang for C AST, etc.) is either:
  - documented as an external developer prerequisite, OR
  - shipped under a license compatible with `Nucleor_OSS`.

### G4 — Substrate-compatibility gates (Nucleor_OSS rules)

These mirror the `Nucleor_OSS` rules captured in `docs/rfcs/v1_REMAINING_PUNCHLIST_AGENT_HANDOFF_v0845_2026-05-07.md`.

- **G4.1** No Python product/toolchain runtime: `nuc port` invocation path must not require `python` on PATH at adopter run-time. Translate's Python-frontend tooling that uses Python to PARSE the source is acceptable as a developer prerequisite, but not as a runtime dependency of `nuc port`'s build chain.
- **G4.2** No vendored Python helpers in OSS-side shim source (`nuc port` shim is Nucleor + shell only).
- **G4.3** No external network access in the verify gate beyond what `Nucleor_OSS` already permits.
- **G4.4** Build artifacts go through the same `bin/nucleor` and `bin/nucleor_tools` pipeline that `Nucleor_OSS` uses; no parallel build system.
- **G4.5** Translate-emitted `.nr` source obeys `Nucleor_OSS`'s strict-mode rules (`nuc build-strict` clean on a curated representative fixture set).

### G5 — Cross-platform parity

- **G5.1** Linux verify and Windows verify produce equivalent PASS counts; any platform-specific exclusions are listed in `Nucleor_Translate/docs/PROGRESS.md` and reviewed by the OSS integration owner.
- **G5.2** Hash-byte parity transcript paired Windows + POSIX for representative `nuc port` outputs (mirrors Lane 7 R06 cross-platform requirement). Evidence is a paired transcript artifact, not just two separate green logs.
- **G5.3** No reliance on WSL/Wine for either platform's evidence (reuse Lane 8 Linux Proof Rule: native Linux only).

### G6 — Provenance / SBOM / supply-chain

- **G6.1** SBOM emitted: `Nucleor_Translate` produces a current SBOM listing every transitive runtime dep with version + license. Stored at integration time as part of the gate evidence.
- **G6.2** `.nucleor_provenance` PE/ELF section embedded in any executable Translate emits (per RFC-0031 / external roadmap Pick C). Section content includes the Translate ref, OSS compiler ref, and source SHAs.
- **G6.3** Reproducible build evidence: independent third-party SHA-256 of `nuctranslate.exe` from a clean checkout on a clean host matches the integration owner's SHA.
- **G6.4** No untracked binary blobs introduced by integration. `git ls-files` enumerates every artifact.

### G7 — Documentation drift

- **G7.1** `docs/PROGRESS.md` reflects the integration ref's actual SPEC state (e.g., if SPEC-12 is being shipped, "SPEC-12 DONE" must appear, not just a "next: SPEC-12" banner).
- **G7.2** README and CLI help text accurately enumerate the supported frontend set at the integration ref.
- **G7.3** No "future work" claims in OSS-shipped docs that imply Translate currently does X when X is not in the integration ref.
- **G7.4** Any `nuc port` CLI help text in `Nucleor_OSS` accurately delegates to Translate documentation rather than restating it (single source of truth).

### G8 — OSS-side integration changes (the shim)

- **G8.1** The OSS-side shim is a thin CLI router: it MUST NOT duplicate Translate's parsing, lowering, or emit logic.
- **G8.2** Shim-only fixtures land under `tests/features/nuc_port_*.nr` and are exercised by `tools/verify.sh`. They cover at minimum: dispatch on `.py/.go/.rs/.c/.ts/.js` extension, error path when Translate is not available, version-mismatch diagnostic.
- **G8.3** Strict tests-pass-on-clean-checkout property: cloning `Nucleor_OSS` fresh and running `bash tools/verify.sh` green when Translate is not on disk (the shim either no-ops, errors clearly, or feature-flags out — the gate explicitly chooses one and documents it).
- **G8.4** Performance gate: the shim invocation does not regress `tools/check_perf_regression.{sh,ps1}` cold-compile or RSS guards.
- **G8.5** Cache hygiene: shim invocations interact correctly with `.nuc_cache` (no stale-cache hits across Translate version bumps; mirrors NUC-FEEDBACK-007 closure).

### G9 — Integration owner sign-off (process)

- **G9.1** The integration record names the integration owner, the Translate integration ref, the OSS integration ref, all merge-base SHAs, and a one-paragraph residual statement.
- **G9.2** All findings/inbox/`*translate*` reports older than the integration ref are linked or marked obsolete.
- **G9.3** The CHANGELOG entry for the OSS release containing `nuc port` cites the Translate ref + signed-tag explicitly.
- **G9.4** A roll-back recipe is documented: which OSS commit reverts the shim cleanly, which Translate ref the OSS gate is pinned to.
