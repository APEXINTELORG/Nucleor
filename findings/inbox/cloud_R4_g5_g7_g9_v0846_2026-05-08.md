## Summary

R4 ships three FFI specializations on top of R3's `enforce_g10_effects`:

  - `FFI-G9-MISSING-ALLOW-DIRECT-FFI` — caller of an `extern fn` lacks `#[effect(direct_ffi)]` and `#[allow_effect(direct_ffi)]`.
  - `UNSAFE-G7-MISSING-ALLOW` — fn body contains `unsafe { }` block and lacks `#[effect(unsafe)]` / `#[allow_effect(unsafe)]`.
  - `FFI-G5-NULL-DEREF` — actual deref-after-extern-call dataflow violation: a binding from a `#[may_return_null]` extern is used without a preceding `ptr_is_null(<binding>)` guard on the same path.

All three at error severity. The opt-in gate (R3) keeps existing rod surfaces — which call extern fns extensively without any G-10 attribute — completely unaffected.

The G-10 vocabulary now includes the new `unsafe` token alongside R3's `frees`, `borrows_mut`, `may_return_null`, `direct_ffi`.

## Path-(a) vs path-(b) decision: **path (b) — opt-in error severity**

The brief lays out two paths for the FFI surface retrofit:

  - **(a)** retrofit every rod-wrapper fn that calls extern with `#[effect(direct_ffi)]` or `#[allow_effect(direct_ffi)]`,
  - **(b)** ship at warning level until per-rod retrofits land.

Survey: 216 `.nr` files under `stdlib/` declare or call `extern fn` (counted via `grep -rl "^extern fn\\|^pub extern fn" --include="*.nr" stdlib/`). 1786 total `extern fn` declarations across that surface. Path (a) is a multi-batch retrofit far outside one R-unit envelope.

**Chosen disposition: path (b)-with-twist — error severity but gated behind the existing R3 attribute opt-in.** The `enforce_g10_effects` cheap textual gate (R3) plus the empty-pairs gate keeps the entire R4 specialization dormant on every existing rod that doesn't opt in. Adopters opt their file in by adding any `#[effect(...)]` or `#[allow_effect(...)]` attribute. Severity stays at error so opt-in callers get strict enforcement; non-opt-in callers see no change. Per-rod retrofit can land incrementally without coordination.

This is structurally stronger than path (b) alone: opting in is a concrete commitment to G-10 discipline, not just a "warn me once" toggle.

## Nucleor-pragmatic G-5 design note

The brief specifies G-5 as deref-after-call dataflow on extern fns returning `*const T` / `*mut T`. Today Nucleor's parser halts on `*const T` / `*mut T` outside extern declarations (line 3012 in compiler/nucleor_s1_compiler.nr — defensive halt, not a parse-table feature). Real Nucleor source uses `i64` for FFI handles by convention.

Two consequences:

  - The extern-table builder's "returns_ptr" flag is set when the decl text contains `*const ` / `*mut ` OR when the decl is preceded by an `#[effect(may_return_null)]` / `#[may_return_null]` attribute. The attribute form is the practical opt-in for current sources.
  - The G-5 violation check fires on ANY use of the binding (deref or pass-through) without a preceding `ptr_is_null(<binding>)` guard, not only on `*<binding>` deref. This matches Nucleor's i64-handle convention where "use the value" is the deref-equivalent.

When raw-pointer substrate lands as a real type, the framework's helpers stay valid — the `*const T` heuristic in `g10_collect_extern_fn_table` already covers that future case.
