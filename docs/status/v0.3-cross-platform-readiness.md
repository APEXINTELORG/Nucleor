# v0.3 Cross-platform readiness audit

Snapshot 2026-04-22, v0.2.51 (audit findings preserved verbatim
— the runtime hasn't gained new `#ifdef _WIN32` blocks since,
so the per-block analysis below remains accurate as of v0.2.102).
Single-file status report for the v0.3 Linux/macOS bootstrap
target tracked in
[`docs/milestones/v0.3.0.md`](../milestones/v0.3.0.md).

## TL;DR

The v0.2 runtime is **substantially Linux/macOS-ready**. The
audit found 33 `#ifdef _WIN32` blocks in the main runtime
(`nucleor_llvm_rt.c`) and 32 more across 7 domain `*_rt.c` files
— **every code-bearing block has a paired POSIX `#else` branch**.
The four "unmatched" blocks the static analyzer flagged are all
single-line `#include <windows.h>` guards, which correctly have
no POSIX equivalent (POSIX systems just don't include the file).

The remaining v0.3 work is **(a) the bootstrap path** (we ship
`bin/nucleor.exe` for Windows; need `bin/nucleor` for Linux/macOS,
which requires a self-host loop on Linux) and **(b) the launcher**
(the POSIX `./nuc` wrapper exists but resolves clang via Linux
distro paths that need testing on real installs). No major
runtime rewrites required.

Audit script (reproducible):

```python
import re
text = open('stdlib/runtime/nucleor_llvm_rt.c').read()
lines = text.split('\n')
in_block = False; has_else = False; gaps = []; total = 0
for i, L in enumerate(lines, 1):
    s = L.strip()
    if re.match(r'#if(def)? .*_WIN32', s):
        total += 1; in_block = True; block_start = i; has_else = False
    elif in_block and re.match(r'#else\b|#elif\b', s): has_else = True
    elif in_block and re.match(r'#endif\b', s):
        if not has_else: gaps.append(block_start)
        in_block = False
print(f'Total: {total}, gaps: {len(gaps)}', gaps)
```

## Concrete v0.3 work plan

### v0.3 phase 1 — bootstrap path

- **Stage:** the `bin/nucleor.exe` Windows binary self-hosts from
  `compiler/nucleor_s1_compiler.nr` (verified — this is the
  v0.2.x fixed-point check).
- **v0.3 path:** copy `compiler/nucleor_s1_compiler.nr` to a
  Linux box, install LLVM 18 + clang, run the same `nuc build
  compiler/nucleor_s1_compiler.nr -o nucleor` invocation through
  a temporary Windows-built bootstrap (or transpile via the
  existing rust_bridge path), and verify the output ELF binary
  produces the same LLVM IR fixed point on a second pass.
- **Risk:** none currently identified. The runtime is already
  POSIX-compatible per the audit above; the compiler source has
  no Windows-specific calls (verified by grep).

### v0.3 phase 2 — launcher

- **Stage:** `nuc.bat` resolves `clang.exe` via
  `NUCLEOR_CLANG_PATH` → `LLVM_SYS_180_PREFIX/bin` →
  `C:\Program Files\LLVM\bin` → PATH. POSIX `./nuc` wrapper
  exists.
- **v0.3 path:** verify the POSIX wrapper resolves clang from
  `/usr/bin/clang-18`, `/usr/local/opt/llvm@18/bin/clang`
  (Homebrew on macOS), and `/opt/homebrew/opt/llvm@18/bin/clang`
  (Apple Silicon Homebrew). Add explicit error message for the
  "no clang found" path with install instructions.

### v0.3 phase 3 — verify gate parity

- **Stage:** `tools/verify.sh` runs 186 / 186 on Windows.
- **v0.3 path:** run the same gate on Linux + macOS.
  Examples 01-18 should run identically. The 7 `tests/rods/`
  socket / process / signal tests exercise OS-specific paths
  that the runtime audit confirms are wired (`socket_rt.c` etc.
  have full POSIX `#else` coverage).
- **Expected gate state on Linux v0.3:** 186 / 186 (the same
  number — no platform-conditional examples).

### v0.3 phase 4 — release artifact

- **Stage:** v0.2.x ships `bin/nucleor.exe` only.
- **v0.3 path:** add `bin/nucleor-linux-x86_64` and
  `bin/nucleor-macos-arm64` as additional binaries committed to
  the repo (matching the Windows pattern), or shift to
  release-tarballs. The source-of-truth bootstrap is the same
  `compiler/nucleor_s1_compiler.nr` for all three.

## What's NOT a v0.3 risk (positive findings)

- **No Windows path-separator hardcoding outside path helpers.**
  The path utilities (`path_separator`, `path_normalize`, etc.)
  added in v0.2.23 already handle both separators interchangeably.
- **No CRT-only function calls in user-facing helpers.** The
  `_putenv_s` / `_mkdir` / `_findfirst` / `gmtime_s` calls all
  have paired POSIX branches (`setenv`, `mkdir`, `opendir`,
  `gmtime_r`).
- **No `<windows.h>` types in public APIs.** `HANDLE`, `DWORD`,
  etc. are confined to the internal mutex / channel / thread
  implementation; the `__nucleor_*` ABI stays at `long long` /
  `const char *`.
- **No assumptions about CRLF.** `str_lines` (v0.2.26) explicitly
  strips `\r` so Windows-CRLF text works on POSIX without
  preprocessing.
- **No assumptions about backslash in paths.** `path_normalize`
  treats `/` and `\` interchangeably; output uses
  `__NUC_SEP` which switches by `_WIN32`.

## Open questions for v0.3 kickoff

1. **Pre-built binary distribution policy** — keep
   `bin/nucleor*` committed (current v0.2 pattern), or shift to
   GitHub Releases with versioned tarballs?
2. **Linux bootstrap host** — which distro is the canonical CI
   target? (Ubuntu 22.04 LTS is the default assumption; Debian
   12, Fedora 39, Arch all work but differ in clang path.)
3. **macOS arch matrix** — Intel x86_64 + Apple Silicon arm64,
   or arm64 only (matching current Apple developer machines)?
4. **CI runner** — GitHub Actions free tier covers Ubuntu +
   macOS; Windows is already implicit via the dev workflow.

These are policy questions for v0.3 kickoff, not technical
blockers.
