| Field | Value |
|---|---|
| **Number** | 0012 |
| **Title** | `nuc-bindgen` — libclang-driven binding generator for C and C-style C++ headers |
| **Status** | Draft |
| **Author** | Joseph Wescott + Claude |
| **Created** | 2026-04-22 |

| **Depends on** | RFC-0001 (`#[ffi_no_*]` attributes), parallel to RFC-0011 (`nuc-cxx`) |

---

## 1. Summary

A standalone tool that reads a C/C++ header file via libclang and
emits Nucleor `extern fn` declarations + a wrapper rod.

```bash
$ nuc bindgen --header /usr/include/sqlite3.h \
              --output stdlib/rods/sqlite.nr \
              --rt-audit stdlib/rods/sqlite.audit.toml
generated 254 extern fn declarations + 18 wrapper functions
```

Generated output:

```nucleor
// stdlib/rods/sqlite.nr — generated by nuc-bindgen, do not edit
#cfile "../runtime/sqlite_shim.c"

extern fn sqlite3_open(filename: *const u8, db_out: *mut *mut Sqlite3) -> i32;
extern fn sqlite3_close(db: *mut Sqlite3) -> i32;
extern fn sqlite3_exec(db: *mut Sqlite3, sql: *const u8, ...) -> i32;
// ... 254 total ...

pub struct Sqlite3 { _opaque: i64 }

pub fn sqlite_open(path: &str) -> Result<Db, SqliteError> { ... }
pub fn sqlite_exec(db: &Db, sql: &str) -> Result<(), SqliteError> { ... }
```

This is the **C-side counterpart to `nuc-cxx` (RFC-0011)**. Together
they cover the full FFI story:
- `extern fn` shims for one-shot bindings (no tool)
- `nuc-bindgen` for C-style libraries with broad surface
- `nuc-cxx` for C++ libraries with STL types and classes

---

## 2. Motivation

Real C libraries have hundreds to thousands of declarations. Hand-
writing `extern fn` decls for sqlite3 (~250 fns), libcurl (~80),
libssl (~hundreds), libgit2 (~700) is prohibitive.

Rust's `bindgen` crate is the gold standard: reads C/C++ headers,
emits Rust `extern fn` decls. We model on it.

Prior art:
- **bindgen** (Rust) — reference design
- **SWIG** — multi-language; older, more complex
- **cffi** (Python) — runtime parsing; not statically typed
- **Zig `@cImport`** — built-in to compiler; convenient

Nucleor's choice: standalone tool (`nuc-bindgen`), invoked from build
script or by hand. Output is committed to source control (no
build-time codegen surprises).

## 3. Design

### 3.1 CLI

```
nuc bindgen --header <path> [options]

Required:
  --header <path>          Input C/C++ header
  --output <path>          Output .nr file

Optional:
  --include <dir>          Add include search directory (repeatable)
  --define <K=V>           Pre-define macro
  --target <triple>        Target triple for ABI choices (default: host)
  --whitelist-fn <regex>   Only emit functions matching pattern (repeatable)
  --whitelist-type <regex> Only emit types matching pattern (repeatable)
  --opaque <type>          Treat type as opaque (no field access)
  --rt-audit <path>        Emit RT-audit manifest TOML (per RFC-0001 §3.5)
  --shim <path>            Emit C shim file alongside the .nr
  --c++                    Treat as C++ (emit extern "C++" decls; less safe)
  --no-derive-debug        Don't auto-derive Debug for generated structs
  --enable-cxx-namespaces  Honor C++ namespaces in name mangling
```

### 3.2 Type mapping (C → Nucleor)

| C type | Nucleor |
|---|---|
| `char` | `i8` (or `u8` if `--char-unsigned`) |
| `signed char`/`int8_t` | `i8` |
| `unsigned char`/`uint8_t` | `u8` |
| `short`, `int16_t` | `i16` |
| `int`, `int32_t` | `i32` |
| `long`, `int64_t` (64-bit OS) | `i64` |
| `size_t` | `usize` |
| `float` | `f32` |
| `double` | `f64` |
| `void*` | `*mut u8` (or `*const u8` if context shows const) |
| `T*` | `*mut T` |
| `const T*` | `*const T` |
| `T[N]` | `[T; N]` |
| `T[]` (incomplete array) | `*mut T` |
| `struct Foo {...}` | `struct Foo { ... }` (with `#[repr(C)]`) |
| `union Foo {...}` | `union Foo { ... }` |
| `enum Foo {...}` | `#[repr(C)] enum Foo { ... }` |
| `typedef X Y;` | `type Y = X;` |
| `_Bool` / `bool` | `bool` |

### 3.3 Bitfield handling

C bitfields are platform-specific. `nuc-bindgen` emits them as
opaque `u32`/`u64` chunks with accessor methods generated from the
known bit layout for the target ABI. Note caveat in output.

### 3.4 Variadic functions

C variadics (`int printf(const char* fmt, ...)`) emitted as:

```nucleor
extern fn printf(fmt: *const u8, ...) -> i32;
```

Nucleor support for `...` in extern decls is added by this RFC
(simple, just a parser + codegen change to forward varargs).

### 3.5 Function-pointer types

C: `typedef int (*Handler)(int, int);`
Nucleor:

```nucleor
type Handler = fn(i32, i32) -> i32;
```

### 3.6 Const correctness

`const T*` emits as `*const T` in Nucleor; non-const as `*mut T`.
The user's wrapper code propagates the const-ness via `&T` vs
`&mut T`.

### 3.7 Wrapper layer

By default, `nuc-bindgen` emits:
- `extern fn` declarations matching the C signatures
- A thin wrapper for each function that:
  - Converts `&str` to `*const u8` (with NUL-terminator check)
  - Converts `&mut Vec<T>` to `*mut T` + length
  - Wraps return values in `Result` based on convention (e.g., `int`
    returns where 0 = success, non-zero = errno)

Convention overrides via `--convention errno` / `--convention zero-success`
/ `--convention pointer-or-null`.

### 3.8 RT-audit manifest

Output of `--rt-audit` is a TOML file that RFC-0001 §3.5 reads:

```toml
# stdlib/rods/sqlite.audit.toml
[functions]
sqlite3_open    = { may_alloc = true,  may_panic = false }
sqlite3_close   = { may_alloc = true,  may_panic = false }
sqlite3_exec    = { may_alloc = true,  may_panic = false }
# nuc-bindgen marks every fn `may_alloc=true` by default;
# the maintainer hand-edits to mark known-safe functions.
```

### 3.9 Composition with `nuc-cxx` (RFC-0011)

Three-tier story:
1. **Hand-written `extern fn`** — small surface, one or two functions.
2. **`nuc-bindgen`** — broad C-style surface (sqlite, libcurl,
   librealsense). Emits flat `extern fn` decls.
3. **`nuc-cxx`** — C++ STL/template-heavy (Drake, Eigen, OpenCV C++).
   Paired declarations.

Bindgen handles ~80% of binding needs in our robotics roadmap (most
robotics SDKs ship C APIs).

### 3.10 Diagnostics

| Code | Meaning |
|---|---|
| BINDGEN-001 | Header file not found |
| BINDGEN-002 | libclang parse error |
| BINDGEN-003 | Type conversion not supported (e.g., complex bitfield) |
| BINDGEN-004 | Forward-declared type with no definition (treated as opaque) |
| BINDGEN-005 | Duplicate symbol (regenerated; check for include guards) |

## 5. Alternatives considered

- **Built-in to compiler (`@cImport`-style Zig)** — coupling. Tool
  is more flexible.
- **Runtime parsing (cffi-style)** — slow, no static typing.
- **Hand-write everything** — current state; doesn't scale.
- **Use a Python-based generator** — adds Python build dep; nuc-bindgen
  is self-contained.

## 6. Open questions

1. Macros — preprocessor macros aren't first-class in C ASTs. Bindgen
   tries to convert `#define FOO 42` to `pub const FOO: i32 = 42;`
   but skips function-like macros. Recommend skip + warning.
2. Anonymous structs/enums — emit with synthetic names (`__bindgen_anon_1`).
3. Inline functions in headers — emit declarations + require user to
   provide a shim implementation. Or auto-generate the shim that
   forwards to a same-named non-inline.
4. Should bindgen output be auto-formatted? Recommend yes (call
   `nuc fmt` on output).
5. Versioning the output for diff-friendliness — yes; deterministic
   ordering, stable comments.

## 8. Future extensions

- Watch-mode (`nuc bindgen --watch` to re-emit on header change)
- Diff-aware regeneration (only re-emit changed decls)
- Support for `#pragma pack` and other layout directives
- Auto-generated test harnesses ("link-time only" tests that all
  symbols exist)
