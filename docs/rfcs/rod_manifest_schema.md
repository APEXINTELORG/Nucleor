# `rod_manifest.toml` schema

Field-by-field reference for `docs/rfcs/rod_manifest.toml`. The
manifest is the source-of-truth catalog for every user-facing rod
in `stdlib/rods/*.nr` — what you reach for via
`import "stdlib/rods/<name>.nr"`. Generated by
`tools/gen_rod_manifest.py` from the `.nr` files themselves.

This is the **rods companion** to
`docs/rfcs/helper_manifest.toml` (the ABI surface). The two
manifests answer different questions:

- **rod manifest** — "what modules can I import?"
- **helper manifest** — "what `__nucleor_*` symbols can the
  compiler emit?"

A rod can call multiple helpers, and a helper can be exposed
through multiple rod functions. The numbers are independent:
121 rods, 676 helpers as of v0.2.46.

## Per-row fields

### `name` — string
The bare rod name (filename without `.nr`). Example: `"math"`.
This is what users write between the quotes in
`import "stdlib/rods/math.nr"`.

### `path` — string
Repo-relative path to the `.nr` file (always
`stdlib/rods/<name>.nr` for v0.2 — kept as a field for forward
compat once nested rod paths land in v0.4 with the resolver).

### `description` — string
The one-line description from the rod's leading comment block.
The generator extracts this from a header line of the form
`// rods/<name> — <description>` (em-dash, en-dash, or colon
separator), or the first informative comment line otherwise.
Empty string if no description could be extracted (those rods
appear in the REVIEW REQUIRED block at the top of the manifest).

### `function_count` — integer
Number of top-level `fn` definitions in the rod (counts both
`fn` and `pub fn`). Includes private helpers — the generator
doesn't yet distinguish exported from internal.

### `cfile_count` — integer
Number of `#cfile <path>` directives in the rod. Each `#cfile`
adds a C source file to the linker command for any program that
imports the rod. Most stdlib rods are zero (the runtime is
pre-compiled into `nucleor_llvm_rt.c`); domain rods like `gpu`,
`fft`, `fluid` typically have one or more.

### `loc` — integer
Source lines, counting non-blank non-pure-comment lines. A rough
"how big is this rod" measure.

### `imports` — list of strings
Other rod names this rod imports (parsed from
`import "stdlib/rods/<name>.nr"` directives). Builds the rod
dependency graph — useful for understanding what a rod pulls in
transitively. Empty list for self-contained rods.

## REVIEW REQUIRED block

If any rod has no extractable description, it's listed under a
`# REVIEW REQUIRED` comment block at the top of the manifest. To
fix: add a leading comment line of the form
`// rods/<name> — <description>` to the rod file and re-run the
generator.

As of v0.2.46, the REVIEW REQUIRED count is **0**.

## Worked example

```toml
[[rod]]
name           = "math"
path           = "stdlib/rods/math.nr"
description    = "Integer math utilities"
function_count = 10
cfile_count    = 0
loc            = 35
imports        = []
```

Reading: `math.nr` exposes 10 functions across 35 LOC, has no
runtime C dependencies (it's pure Nucleor), and imports no other
rods (self-contained).

## Re-generating the manifest

Whenever a rod is added or modified:

```bash
python tools/gen_rod_manifest.py
```

This overwrites `rod_manifest.toml` from the `.nr` source. Unlike
`helper_manifest.toml`, the rod manifest is **not** currently
gate-enforced — adding a rod without regenerating the manifest
won't fail the verify gate today. (Wiring it into
`tools/check_compiler_drift.sh` is a follow-up release; the
helper manifest got priority because the helper ABI is more
load-bearing.)

## Going-forward expectation (v0.2.46+)

When adding a new rod, regenerate the manifest in the same
commit. The eventual gate enforcement will require this.
