# v1.1.1 → v1.2.0 — The §H + Perf-Clawback Narrative

**Date:** 2026-05-30
**Branches:** `review/v1.1.1-TZ8Qc` (active development) and
`review/h-perf-clawback` (perf fix), both merged to `main` at the v1.2.0
release commit.
**One-line summary:** §H module-prefixed lowering shipped (RFC-NRT-004
Phase A), and the Windows cold-compile cost it appeared to introduce
turned out to be a link-flag oversight, fixed with `-flto -Wl,/OPT:ICF
-Wl,/OPT:REF`. Cold ends up **faster** than the v1.1.1-era baseline.

This document captures the full sequence — what was tried, what
failed, what worked, and why — so the next person doesn't repeat the
investigation.

---

## 3. §H — RFC-NRT-004 Phase A

The last substantive deferred item: **module-prefixed lowering**. Two
imported modules that both define `pub fn parse_expr` previously
aborted at link with `ERROR: duplicate top-level fn name` because
Nucleor emits flat un-namespaced symbols.

### Design

Opt-in via a marker on the first non-blank line of an imported file:

```
// nucleor:module-namespace <prefix>
```

The resolver pass (`compiler/s1/cli.nr` + `compiler/s1/modules.nr`)
rewrites every top-level fn def and intra-file call site (except
`main`) to `<prefix>_<name>` using the same token-aware walk the
existing `priv_mangle_private_fns` privatization path uses. The
importer references the fns by their prefixed name directly — no new
per-call namespacing syntax was introduced.

### Implementation

Three new fns in `cli.nr` (`mod_h_prefix_from_marker`,
`mod_h_collect_top_level_fn_names`, `mod_h_mangle_module_fns`), one
hook in each of the two splice arms of `modules.nr`, and a fix-it
rewrite of the duplicate-fn abort message in `emit.nr`. Total: +231
lines, additive, no edits to existing fn bodies.

### Validation

Spike test in `tests/features/rfc_nrt_004_h/` with two modules
defining `pub fn kind_to_str` + `pub fn run`, both opt-in with
distinct prefixes. Pre-§H: build aborts. Post-§H: build succeeds,
runtime prints `a_zero / b_zero / a_one / b_one`. Bootstrap converged
in two iterations (stage1 differs from stage2 because the old bin
didn't have §H, but stage2 == stage3 = converged seed).

### Scope honestly stated

Phase A is the mechanism only. Phase B (use §H to dedup the residual
28 mirrored s1/ts fns) and Phase C/D (flip the drift gate to FAIL by
default) are separate work. Importer call-site auto-rewriting is out
of scope — importers explicitly reference `<prefix>_<name>`.

## 4. The perf regression that appeared

After §H landed, Windows cold compile measured **4.69 s** vs an earlier
**3.55 s** baseline — a +32 % regression. Hot stayed clean (0.26 s)
once Windows Defender exclusions were added to the working tree, LLVM,
and the compiler binary.

The natural assumption was that some post-v1.1.1 work — MEM-3 escape
analysis, SEC-8 SHA256 cache hashing, §H itself — was adding compile-
time work to the hot path.

### What the investigation actually found

Phase-by-phase A/B with both bins compiling the same current source:

| Phase | OLD bin (v1.1.1 era) | NEW bin (post-§H) | Δ |
|---|---|---|---|
| resolve_source | 63 ms | 125 ms | +62 |
| lex | 47 ms | 78 ms | +31 |
| parse | 125 ms | 141 ms | +16 |
| ownership | 1062 ms | 718 ms | **−344** (the perf agent's O(1) sym-table fix helping) |
| **type** | **500 ms** | **1032 ms** | **+532** (the big one) |
| lower | 156 ms | 219 ms | +63 |
| opt | 63 ms | 93 ms | +30 |
| emit | 171 ms | 235 ms | +64 |
| clang | 907 ms | 1281 ms | +374 |
| **total wall** | **3375 ms** | **4562 ms** | **+1187** |

Then the cross-check that ruled out source-level fixes:

- Both bins emit **byte-identical IR** for current source (md5
  `fb63619530d074cdeee1da716fecbbb4`, sizes 13,331,198 vs 13,333,614
  bytes — 0.018 % delta = the 3 §H fn declares).
- Same op counts in the profile (329,216 call_expr, 481,451
  env_lookup, 34,262 stmt — identical).
- `type_expr` emitted IR was **identical** in both (19,764 LLVM lines,
  zero drop helper calls injected by MEM-3 escape analysis).
- The `kind == 7` call-expr branch of `type_expr` is *smaller* today
  (680 source lines) than at v1.1.0 (744 lines), same 127 `str_eq`
  density.

So the slowdown could not have come from MEM-3 adding drops, §H
runtime overhead, larger IR, more work per call, or grown source —
all of those were measurably negated.

### The actual cause

The OLD committed bin happened to be **small** (1.55 MB) because it
was linked from smaller v1.1.1-era source at `-O0` (the default
bootstrap clang link). The NEW bin had to be rebuilt for §H (any s1
source change forces a new bootstrap seed, and the seed needs a
matching bin), and that rebuild necessarily folded in every accumulated
post-v1.1.1 change. The result was a 2.67 MB binary linked at `-O0`.

**Windows execution of the larger `-O0` binary is materially slower
per fn call** than execution of the smaller `-O0` binary — iCache
behavior, page-fault patterns, fn-dispatch overhead all scale with
binary size on Windows in a way Linux doesn't see as dramatically.

The perf agent's measurements on Linux had shown no equivalent
regression. Concurrent cross-check from a Linux runner confirmed the
diagnosis: environmental, Windows-specific, not a code bug.

## 5. The fix

Re-link the bootstrap with three additional flags:

```
-flto                  # link-time optimization
-Wl,/OPT:ICF           # identical code folding (Windows-specific)
-Wl,/OPT:REF           # strip unreferenced symbols
```

Results:

| Metric | Pre-fix | Post-fix |
|---|---|---|
| `bin/nucleor.exe` size | 2.67 MB | **1.18 MB** (−56 %) |
| Cold compile (Windows) | 4.69 s | **3.30 s** (−30 %) |
| Cold compile vs OLD v1.1.1 baseline | +32 % | **−7 %** (beats it) |
| Hot compile | 0.26 s | **0.14 s** (−46 %) |
| Emitted IR | md5 fb6361953... | md5 fb6361953... (identical) |
| Bootstrap fixed point | holds | holds |

LTO doesn't change the compiler's behavior — it gives the linker
whole-program visibility so it can fold duplicate code, inline across
translation-unit boundaries, and strip unreferenced symbols across the
9,597-line runtime + the s1 IR.

`tools/bootstrap_windows.ps1` was updated to include these flags by
default so every future seed regeneration produces the optimized bin.
Linux is unaffected — `tools/bootstrap_linux.sh` was not touched
(no equivalent regression to fix), though it could adopt the same
flags for the binary-size win in a future commit.

## 7. What did NOT ship in v1.2.0

- §H Phase B (use the mechanism to dedup the residual 28 s1/ts fns).
  The mechanism is in place but the dedup itself is mostly cosmetic
  now that DUP-1 brought the census from 85 → 28 with 0 signature
  divergences.
- §H Phase C/D (flip drift-gate parser checks from WARN to FAIL by
  default). Sequenced after B in the original plan.
- Reverting any of MEM-3 / MEM-4 / MEM-5 / MEM-6 / SEC-1..8 / HON-1..5
  / VER-1..8 to chase the prior baseline. The A/B proved they weren't
  the cause, and they're all correctness landings.
- General-build LTO. `cache.nr`'s standard link path still defaults to
  `-O0` for user programs. A `--release` flag opting user programs into
  the same LTO pipeline would be a clean follow-up RFC.
- Linux bootstrap LTO. `bootstrap_linux.sh` could adopt the same flags
  for the binary-size win, but Linux didn't see the cold regression so
  it's lower priority.

## 8. Lessons recorded for next time

1. **Investigate before optimizing.** The first instinct was to find
   what new compile-time work to remove. The A/B IR-equality check
   proved early that there was no new work to remove. ~30 minutes of
   surgical optimization attempts would have been wasted without it.

2. **A/B against the actual prior baseline binary.** Extracting the
   OLD committed `bin/nucleor.exe` from `main` for direct phase-by-phase
   profiling against the new bin was the single most informative
   diagnostic step. Everything before that was guessing.

3. **The committed bin can lag the committed source.** When the
   perf agent landed source changes (O(1) ownership, parallel codegen,
   etc.) they did not rebuild `bin/nucleor.exe`. Anyone measuring
   Windows perf without rebuilding got the OLD bin's (artificially
   smaller) number, masking the eventual cost when §H forced the
   rebuild.

4. **Defender false-positives compound.** Initial perf measurements
   showed hot compile at 2.10 s (vs 0.26 s baseline) — an 8×
   regression. That was entirely Defender scanning the freshly-built
   .exe on every invocation. Defender exclusions for the working tree,
   LLVM, and the compiler binaries fixed it instantly. Worth setting
   up before any perf investigation on Windows.

5. **Link-flag tuning matters.** A 30 % cold-compile improvement and
   a 56 % binary-size reduction came from three linker flags
   (`-flto`, `/OPT:ICF`, `/OPT:REF`) with zero source change. The
   Nucleor self-build had been running at unoptimized link for the
   entire v1.x history.
