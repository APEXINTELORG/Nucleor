# Nucleor v0.3 — Robotics RT Guide

> **Audience:** writing real-time control loops in Nucleor (PID,
> motor control, sensor fusion, deadline-bound state machines).
> **Status:** every attribute and diagnostic listed here is wired
> end-to-end as of v0.3.24 with v1 source-level enforcement, smoke
> coverage, and verify-gate steps.

The v0.3.x ship arc landed RFC-0001 in full plus the extern-C
shim generator. This guide collects everything in one place so
you can read a single page and start writing real-time-correct
Nucleor today.

## TL;DR — the L1 hard real-time bundle

```nucleor
#[no_alloc]
#[no_panic]
#[no_dyn]
#[deadline = 100]
fn pid_step_rt(kp: i64, ki: i64, kd: i64,
               err: i64, integral: i64, last_err: i64) -> i64 {
    let derivative: i64 = err - last_err;
    let p_term: i64 = kp * err;
    let i_term: i64 = ki * (integral + err);
    let d_term: i64 = kd * derivative;
    return p_term + i_term + d_term;
}
```

Compile-time guarantees this fn body:

- Allocates nothing on the heap (`#[no_alloc]` -> RT-001).
- Has no panic-prone calls (`#[no_panic]` -> RT-002).
- Uses no dynamic dispatch (`#[no_dyn]` -> RT-003).
- Comes in under 100 microseconds wall-clock (`#[deadline = 100]`
  -> RT-004 runtime + static estimator).

The full worked example lives at
[`examples/19_rt_pid.nr`](../examples/19_rt_pid.nr).

## Attribute reference

| Attribute              | Purpose                                          | Diagnostic |
|------------------------|--------------------------------------------------|------------|
| `#[no_alloc]`          | Forbid heap allocation in this fn body           | RT-001     |
| `#[no_panic]`          | Forbid panic-prone calls (`unwrap`, `assert`, …) | RT-002     |
| `#[no_dyn]`            | Forbid dynamic dispatch (`dyn Trait`, `Box<dyn>`)| RT-003     |
| `#[deadline = N]`      | Wall-clock budget in microseconds                | RT-004     |
| `#[max_depth = N]`     | Bound recursion in a `#[deadline]` fn            | (opts out RT-008) |
| `#[allow(<CODE>)]`     | Suppress one diagnostic file-wide                | (filter)   |
| `#[deny(<CODE>)]`      | Promote a warning to an error file-wide          | (promote)  |
| `#[allow_fn(<CODE>)]`  | Suppress one diagnostic for the next fn only     | (filter, v0.3.20) |
| `#[deny_fn(<CODE>)]`   | Promote a warning to error for the next fn only  | (promote, v0.3.21) |
| `#[ffi_no_alloc]` (extern) | Mark an `extern fn` as RT-safe for `#[no_alloc]` callers | (filter, v0.3.24) |
| `#[ffi_no_panic]` (extern) | Mark an `extern fn` as RT-safe for `#[no_panic]` callers | (filter, v0.3.24) |
| `#[export]`            | Make a fn callable from C via `nuc gen-headers`  | (codegen)  |
| `#[repr(C)]` (struct)  | C-ABI-compatible struct layout                   | (codegen)  |

## Diagnostic reference (RFC-0001 §3.5)

Every code from the spec table now has v1 source-level
enforcement, smoke coverage, and (where applicable) a negative
fixture.

| Code   | Severity | Fires when                                                              | Shipped |
|--------|----------|-------------------------------------------------------------------------|---------|
| RT-001 | error    | `#[no_alloc]` fn body calls an alloc-prone builtin                      | v0.2    |
| RT-002 | error    | `#[no_panic]` fn body calls a panic-prone builtin                       | v0.3.1  |
| RT-003 | error    | `#[no_dyn]` fn signature/body uses `dyn`                                | v0.3.5  |
| RT-004 | warning + abort | Static WCET estimate exceeds budget; runtime overrun aborts        | v0.3.0 + v0.3.2 |
| RT-005 | warning  | RT-marked fn calls an unmarked `extern fn` (FFI is opaque)              | v0.3.8 + v0.3.24 opt-out |
| RT-006 | error    | RT attribute attached to an `async fn`                                  | v0.3.7  |
| RT-007 | warning  | `#[deadline]` without `#[no_alloc]` or `#[no_panic]`                    | v0.3.3  |
| RT-008 | warning  | Direct self-recursion in `#[deadline]` fn lacks `#[max_depth]`          | v0.3.9  |

All warnings are suppressible per-file via `#[allow(RT-NNN)]`.
Errors are not suppressible by design.

## extern-C interop

`nuc gen-headers` walks the source for three kinds of
declarations and emits a matching C header:

- `extern fn name(...) -> ret;` — fn declared in C, called from
  Nucleor (the import direction).
- `#[repr(C)] struct Name { ... }` — struct usable across the
  ABI boundary in either direction.
- `#[export] fn name(...) -> ret { ... }` — fn defined in
  Nucleor, callable from C through the unmangled LLVM symbol
  (the export direction; v0.3.4).

```bash
nuc gen-headers tests/fixtures/t34_export.nr -o nucleor_kernel.h
# nuc gen-headers: wrote 1 #[repr(C)] struct(s),
#                  1 extern decl(s),
#                  3 #[export] decl(s) to nucleor_kernel.h
```

The host C/C++ build then `#include "nucleor_kernel.h"` and
links against the Nucleor-built `.o` directly — no FFI wrapper
hand-rolling required.

## Cookbook

Four common patterns you'll write the day you reach for the v0.3
attribute family. Each one is copy-paste-ready and points at a
fixture you can run under the verify gate.

### 1. Basic PID step (full L1 stack)

The four-attribute sandwich on a tight inner loop. The driver
fn that calls the step is intentionally NOT RT-annotated —
`print` and `str_concat` allocate, so they live outside the
RT contract.

```nucleor
#[no_alloc]
#[no_panic]
#[no_dyn]
#[deadline = 100]
fn pid_step_rt(kp: i64, ki: i64, kd: i64,
               err: i64, integral: i64, last_err: i64) -> i64 {
    let derivative: i64 = err - last_err;
    return kp * err
         + ki * (integral + err)
         + kd * derivative;
}
```

→ Full driver in [`examples/19_rt_pid.nr`](../examples/19_rt_pid.nr).

### 2. Sensor reading with `#[no_panic]` only

When the inner loop is cheap enough that you don't care about
WCET but you DO care that it can't unwrap or assert. Drop the
deadline + no_alloc to avoid RT-007 noise on a fn whose only
constraint is "never panic".

```nucleor
#[no_panic]
fn sample_clamp(raw: i64, lo: i64, hi: i64) -> i64 {
    if raw < lo { return lo; };
    if raw > hi { return hi; };
    return raw;
}
```

The compiler statically rules out `unwrap`, `expect`,
`assert_eq`, `assert_ne`, and the `panic!` builtin. Caller
code is free to allocate / dispatch / take its time; the
no-panic guarantee is the only one that propagates.

### 3. State-machine step with bounded recursion

A `#[deadline]` fn that recurses on purpose (e.g. tree walk,
iterative-deepening, ladder logic resolver). The
`#[max_depth = N]` annotation tells the v0.3.9 RT-008 check to
shut up about the recursion — you've declared the bound.

```nucleor
#[deadline = 500]
#[no_alloc]
#[max_depth = 8]
fn fib_bounded(n: i64) -> i64 {
    if n <= 1 {
        return n;
    };
    return fib_bounded(n - 1) + fib_bounded(n - 2);
}
```

→ Verify gate fixture: [`tests/fixtures/t310_rt008_bounded.nr`](../tests/fixtures/t310_rt008_bounded.nr). The matched negative
fixture [`tests/fixtures/t310_rt008_recursion.nr`](../tests/fixtures/t310_rt008_recursion.nr) shows the same fn WITHOUT
`#[max_depth]` firing the warning.

### 4. Per-fn diagnostic control (`#[allow_fn]` / `#[deny_fn]`)

The file-wide `#[allow(CODE)]` and `#[deny(CODE)]` attributes
shipped in v0.2.151 / v0.2.152 are blunt instruments — they
turn one diagnostic on or off across the entire compilation
unit. v0.3.20 + v0.3.21 add per-fn variants for cases where
one fn has stricter or looser requirements than the rest of
the file.

```nucleor
// Loose orchestration fn — RT-007 fires here as a warning,
// build still succeeds. The author saw it, decided the
// trade-off is fine, and moved on.
#[deadline = 1000]
fn poll_loop(x: i64) -> i64 {
    return x + 1;
}

// Critical inner loop — same constraint, but the contract is
// stricter. #[deny_fn(RT-007)] promotes the warning to error
// for THIS fn only. Build fails until the author either adds
// the missing #[no_alloc] / #[no_panic] OR (if the constraint
// is genuinely spurious) explicit #[allow_fn(RT-007)].
#[deadline = 1000]
#[deny_fn(RT-007)]
fn motor_step(x: i64) -> i64 {
    return x + 1;    // build error: RT-007 promoted
}

// Acknowledged exception — this fn legitimately can't satisfy
// the cross-check (e.g. unbounded sensor read) but the author
// has audited it. #[allow_fn(RT-007)] suppresses just this
// diagnostic, just for this fn — the rest of the file's RT-007s
// still surface.
#[deadline = 1000]
#[allow_fn(RT-007)]
fn known_unbounded_sensor_read(x: i64) -> i64 {
    return x + 1;    // RT-007 silenced for this fn only
}
```

The pair lets a package set a default policy and then carve
out per-fn exceptions in either direction. Errors stay
non-suppressible by design — `#[allow_fn]` / `#[deny_fn]` only
move things across the warning ↔ error line, not into or out
of nothing.

→ Verify gate fixtures: [`tests/fixtures/t320_allow_fn.nr`](../tests/fixtures/t320_allow_fn.nr) (allow), [`tests/err/err_t321_deny_fn.nr`](../tests/err/err_t321_deny_fn.nr) (deny).

### 5. RT-safe `extern fn` markers (`#[ffi_no_alloc]` / `#[ffi_no_panic]`)

By default v0.3.8's RT-005 warns whenever an RT-marked fn body
calls into ANY `extern fn`, because the compiler can't see what
the C side does. The blunt opt-out is `#[allow(RT-005)]` at the
file level, which silences the diagnostic for every extern in
the file.

v0.3.24 adds per-symbol opt-outs — annotate the `extern fn`
declaration itself, and RT-005 stops firing for THAT extern
specifically while still flagging every other unmarked one.

```nucleor
// Trusted FFI — host promises it doesn't allocate. RT-005 will
// not fire on calls to this from #[no_alloc] bodies.
#[ffi_no_alloc]
extern fn host_get_time() -> i64;

// Trusted FFI — host promises it doesn't panic. RT-005 will not
// fire on calls to this from #[no_panic] bodies.
#[ffi_no_panic]
extern fn host_log(msg: i64) -> i64;

// Unmarked — opaque to the compiler. RT-005 still fires from
// any RT-marked caller.
extern fn host_send_packet(buf: i64, len: i64) -> i64;

#[no_alloc]
fn rt_caller(buf: i64, len: i64) -> i64 {
    let t: i64 = host_get_time();          // OK — marker says safe
    let _: i64 = host_send_packet(buf, len); // RT-005 fires
    return t;
}
```

Two contracts give you four practical combinations:

- `#[ffi_no_alloc]` only — extern is safe to call from
  `#[no_alloc]` bodies, still flags from `#[no_panic]` bodies.
- `#[ffi_no_panic]` only — extern is safe to call from
  `#[no_panic]` bodies, still flags from `#[no_alloc]` bodies.
- Both markers — extern is safe to call from `#[no_alloc]`,
  `#[no_panic]`, AND `#[deadline]` bodies (deadline-determinism
  subsumes both no-* contracts, so the intersection of marked
  externs is what RT-005 considers safe for `#[deadline]`).
- Neither — opaque, RT-005 fires from any RT-marked caller.

These are author-asserted contracts, not proofs — the compiler
trusts the marker. The right rule of thumb is: mark FFI symbols
you wrote (or read source for) and audited against the
no-alloc / no-panic guarantee. Leave third-party imports
unmarked so RT-005 keeps reminding you they're opaque.

→ Verify gate fixture: [`tests/fixtures/t324_ffi_no_alloc.nr`](../tests/fixtures/t324_ffi_no_alloc.nr).

### 6. C-side caller of an `#[export]`ed Nucleor fn

Robotics middleware (ROS, microROS, RTI Connext, custom EtherCAT
masters) usually owns the main loop and wants to call into
Nucleor for a single RT-tight kernel. The v0.3.4 `#[export]`
surface plus `nuc gen-headers` gives you a C-callable signature
without writing FFI glue.

Nucleor side:
```nucleor
#[repr(C)]
struct Vec3 { x: f64, y: f64, z: f64 }

#[export]
fn nuc_dot(a: Vec3, b: Vec3) -> f64 {
    return a.x * b.x + a.y * b.y + a.z * b.z;
}
```

Generate the header:
```bash
nuc build kernel.nr -o kernel    # produces kernel.exe and kernel.o
nuc gen-headers kernel.nr -o kernel.h
# nuc gen-headers: wrote 1 #[repr(C)] struct(s),
#                  0 extern decl(s),
#                  1 #[export] decl(s) to kernel.h
```

C side:
```c
#include "kernel.h"

int main(void) {
    Vec3 a = { 1.0, 2.0, 3.0 };
    Vec3 b = { 4.0, 5.0, 6.0 };
    double dp = nuc_dot(a, b);    // 32.0
    return 0;
}
```

Link the C binary against `kernel.o` directly — no FFI wrapper
hand-rolling required. Symbol name is unmangled
(`nuc_dot`, not `_ZN6kernel...`) because the LLVM IR emits it
that way; that's the contract `#[export]` promises.

→ Verify gate fixture: [`tests/fixtures/t34_export.nr`](../tests/fixtures/t34_export.nr).

## v1 limitations and what's deferred to v0.4

The v0.3.x checks are deliberately source-level v1
implementations. Each is a substring/text-walk over the
post-resolver source, with the strip pass from v0.3.6 masking
out string literals and `//` comments before scanning. This is
fast, predictable, and fails-safe in the same direction
(false positives, suppressible) — but it's not an AST
analyzer. The known v1 limitations:

- **RT-001/002/003 string-literal escapes** — fixed by the
  v0.3.6 strip pass. A forbidden token inside `"..."` no longer
  false-triggers; doc strings explaining what's banned are safe.
- **RT-005 ffi-no-* annotation** — shipped in v0.3.24. The
  per-symbol opt-outs `#[ffi_no_alloc]` and `#[ffi_no_panic]`
  on `extern fn` declarations let trusted FFI symbols slip
  through RT-005 individually; see Cookbook §5. The text-walk
  collector matches `<marker>\nextern fn NAME(...)`; the v0.4
  AST-based check will tighten the matcher and add cross-file
  visibility for marker propagation through re-exports.
- **RT-008 indirect recursion** — only direct self-recursion
  fires today (v0.3.9 walks the post-resolver inner body for
  the wrapper's own name). Mutual recursion (A → B → A) needs
  a call graph and is left for the v0.4 AST-based check.
- **RT-004 static WCET v1 estimator** — coarse multiplier ladder
  (no whiles → ×1, 1 → ×100, 2 → ×1000, 3+ → ×10000) capped at
  10⁶ units. Designed to flag obviously-wrong budgets at compile
  time without producing precision noise. v0.4 introduces an
  AST-based v2 estimator that tightens the bounds.

## Self-host fixed-point invariant

Every commit that touches `compiler/nucleor_s1_compiler.nr`
preserves the two-iteration LLVM IR fixed point:

```bash
nuc build compiler/nucleor_s1_compiler.nr -o stage_b
cp target/stage_b.exe bin/nucleor.exe
nuc build compiler/nucleor_s1_compiler.nr -o stage_c
nuc build compiler/nucleor_s1_compiler.nr -o stage_d
diff target/stage_c.ll target/stage_d.ll  # must be byte-identical
```

The verify gate's "self-host rebuild closes" step enforces this
on every release (the bootstrap currently lands at fixed point
SHA `8de96dcb` as of v0.3.28). If you contribute a compiler
change that breaks the fixed point, the gate will block the
merge.
