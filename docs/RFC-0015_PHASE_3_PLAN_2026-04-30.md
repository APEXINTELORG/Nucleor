# RFC-0015 Phase 3 — IR Width-Tagged Numeric Ops: Plan + How + When

**Drafted:** 2026-04-30 (post v0.4.194)
**Author:** Main agent
**Goal:** Move the compiler's LLVM IR emit from uniform `i64`
to width-correct types (`i8`/`i16`/`i32`/`i64`/`u*`) for
narrower-than-64 numeric bindings.

---

## Why this is the keystone for the remaining v0.4 boxes

Two of v0.4.0's six success-criteria boxes are still open and
**both pivot on this work**:

1. **"Strict-mode numerics is the default"** — adopter
   declares `let x: i32 = ...` expecting i32 semantics; today the
   compiler emits `alloca i64` + `add i64` regardless. Strict-mode
   needs width-correct emit before the flag flip is meaningful.
2. **"Every DEFERRED-from-v0.2 row flipped to DONE"** — the
   RFC-0015 phases 3+5+7 row covers exactly this. Phase 3 is the
   IR/codegen migration; phase 5 is stdlib audit; phase 7 is
   verify gate green.

There's also one **probe-agent finding** sitting in
`findings/inbox/_questions.md` (the i16/u8 `print_int` silent
miscompute) that would be cleaned up by phase 3.

---

## Surface — actual size of the migration

`grep -cE 'add i64|sub i64|mul i64|alloca i64|store i64|load i64'
compiler/nucleor_s1_compiler.nr` returns **8 hits**, all
concentrated in the `emit_inst` function at lines ~5050–5130.

The IR ops that need width awareness:

| Op kind | Line | What it emits today |
|---|---|---|
| 0 (binop add) | 5069, 5061 | `add i64 X, Y` |
| 1–7 (binop sub/mul/div/mod/and/or/xor) | similar | `<op> i64 X, Y` |
| 16 (alloca) | 5086 | `alloca i64` |
| 17 (load) | 5087 | `load i64, ptr ...` |
| 18 (store) | 5088 | `store i64 X, ptr ...` |
| 26 (param ref) | 5129 | `add i64 %p.N, 0` |

Plus the `narrow_via_as` helper at line 16463 which already exists
for the narrowing direction, and `widen_via_as` (need to add) for
the widening direction.

The IR op encoding is in `mk_ir_inst` and friends. To make the
emit width-aware, **each IR op needs to carry the operand width**.
Either:
- (A) Embed width in the op kind (kind-N for i32 add, kind-M for
  i64 add, etc.) — explodes the kind space.
- (B) Add a width field to every IR instruction (one extra slot
  per instruction) — uniform but pays cost on every op.
- (C) Look up the width at emit time via the dest register's
  declared type (sym table lookup) — no IR changes, but requires
  threading the type info into the emit context.

**Recommendation: (C).** No IR shape change. The cost is one
sym lookup per emit, which is tiny relative to the LLVM clang
work that follows. Backwards-compatible if the width-lookup
returns "i64" by default.

## Phased ship plan

### Phase 3a (single ship) — Add width-aware emit at allocas/loads/stores

**Scope:**
- `emit_inst` ops 16/17/18: emit `alloca <T>`, `load <T>, ptr ...`,
  `store <T> X, ptr Y`.
- `<T>` derived from the dest register's declared type via a
  new `reg_llvm_type(reg_id) -> str` helper that returns
  `"i64"` (default), `"i32"`, `"i16"`, `"i8"`, `"i1"` (bool), etc.
- All BINOPS still emit `<op> i64`. Sext at load-from-narrower
  to widen back to i64 for arith.

**What stays at i64:** all binops, all calls, all comparisons.

**Sext / zext insertion at boundaries:** when load reads a
narrower type and the user is into i64 arith, emit `%w =
sext iX %r to i64` between the load and the arith. Same pattern
in reverse for stores.

**Risk:** medium. Touches every let-binding's storage. Existing
tests SHOULD still pass because the integer values round-trip
correctly through narrow→wide→arith→narrow.

**Expected perf delta:** +5–10% hot self-build (more emit work
per binding). Hot ceiling 0.97s; current 0.89s; phase 3a likely
lands at ~0.95s. Acceptable.

**Verify gate:** likely 218/1 → 218/1 if the existing i16/u8
fixture (the `print_int` case) is fixed. Possible 217/2 if a
fixture relies on sloppy width behavior.

**Estimated effort:** ~80 lines of compiler edits + 2–3 fixture
adjustments.

### Phase 3b (single ship) — Width-aware binops

**Scope:**
- `emit_inst` ops 0–7: emit `<op> iX %r, %r` where X is the
  operands' width.
- Operand width derived same as 3a.
- Sext / zext at load-time goes away: arith happens at narrow
  width, only widens for cross-width interactions.

**Risk:** higher. Touches every `+ - * / % & | ^` site. Existing
fixtures will compile differently — fixtures using i32 with values
> 2^31 will start panicking at runtime where they used to silently
work (this is a feature, not a bug — but adopters need warning).

**Expected perf delta:** +10–20% hot self-build. Combined with
3a, hot might land at 1.05s — **OVER the 0.97s ceiling**. Will
need ceiling rebase before this ship.

**Verify gate:** likely several fixture adjustments needed.
Estimate 5–10 fixtures touched.

**Estimated effort:** ~150 lines of compiler edits + 5–10
fixture adjustments.

### Phase 3c (single ship) — Width-aware function call ABI

**Scope:**
- Calls to user fns with narrower-typed parameters: pass at
  declared width, not auto-widen to i64.
- Calls to runtime helpers (`__nucleor_print_i64`, etc.):
  insert `sext iX to i64` at the call site for narrower args.
  Closes the i16/u8 `print_int` silent miscompute.
- Function returns: same — return at declared width, sext at
  caller side if cross-width.

**Risk:** medium-high. Runtime helpers all currently take i64.
A clean fix needs sext/zext at the call boundary, NOT changes
to the runtime ABI.

**Verify gate:** stdlib rod call sites need audit (~50 rods
× 5 helpers each = ~250 sites). Most are i64 already.

**Estimated effort:** ~50 lines of compiler edits + audit pass.

### Phase 3d (single ship) — Stdlib audit + verify migration

**Scope:**
- Walk every stdlib rod and confirm narrow-typed bindings now
  produce expected runtime behavior.
- Add `tests/features/rfc0015_phase3_widths.nr` — exhaustive
  fixture covering i8/i16/i32/u8/u16/u32 arithmetic, overflow
  edges, mixed-width binops with explicit `as` casts.

**Risk:** low — pure verification ship.

**Verify gate:** +1 fixture, expect 219/1.

### Phase 3e (single ship, optional) — Strict-mode flip

**Scope:**
- Enable strict-mode numerics by default (was opt-in).
- Update CHANGELOG migration notes for adopters whose v0.2-era
  code relied on i32→i64 implicit widening.

**Risk:** very high — this is the adopter-breaking ship.

**Verify gate:** likely many fixture adjustments. Consider a
pre-ship `nuc fix --numeric` mass-rewrite first.

## How to start

**Today (zero-perf-risk start):**
- ✅ This plan doc itself (this ship).
- Identify and document the 8 IR-emit sites + their type-source
  (which sym entry tells you the width). Also today.

**First execution ship (phase 3a) — when:**
- Probe agent has fully integrated and is on a stable rebase
  cadence (so we don't fight rebase conflicts in `compiler/*.nr`).
- A clean session starts (so the v0.4.194 perf baseline of 0.89s
  hot is the baseline being measured against).
- After updating `findings/_heartbeat.md` "Where we are right now"
  to `phase 3a in flight — probe agent steer clear of emit_inst`.

**Recommended first-execution plan:**
1. Add `reg_llvm_type(reg_id) -> str` helper that returns the
   declared type for a destination register, defaulting to "i64".
   Test: 0 effect on any existing emit (returns "i64" everywhere).
   Should ship green.
2. Wire `reg_llvm_type` into op 16 (alloca) only. Verify all 218
   tests still pass with the same SHA-256 output (T1.7 holds).
   Why: alloca size doesn't affect arith semantics; if narrower
   alloca is correct, the `sext iX to i64` at load time produces
   identical i64 values.
3. Add op 17 (load) with `sext iX to i64` after the load. Same
   T1.7 check.
4. Add op 18 (store) with `trunc i64 to iX` before the store.
   Same T1.7 check.
5. Phase 3a complete. Ship.

Each of those 5 steps could be a sub-ship, OR the whole 3a as
one ship. **Recommended: one ship, comprehensive 3a.** Easier to
audit, easier to revert.

## When NOT to start

- During an active probe-agent integration cycle (rebase pain).
- Mid-session when you've already shipped 30+ tags (cognitive
  fatigue → bugs).
- When the cron is actively re-firing every 5 min (unrelated
  noise + interruption risk).
- Before tightening or rebasing the perf baseline if cold has
  drifted (so we have honest measurement).

---

## When IS the right time

The cleanest scenario:
1. Fresh session start.
2. Probe agent has no `ready_for_integration` queue.
3. Perf baseline stable (last rebase was cold ≤ 3.20s, hot ≤ 0.92s).
4. Main agent has 4+ hours of focused time blocked off.
5. Verify gate currently green at 218/1.

Today's session has met (3) and (5) but is past the focused-time
window — 33 ships in already, marginal-risk increasing.

**Recommended:** start Phase 3a at next session start. Today
this plan doc is the deliverable.

## Rollback plan (per-phase)

Every phase ship's commit is independently revertable. If phase
3a breaks the verify gate or pushes hot perf > 0.97s:

```sh
git revert <phase-3a-commit-sha>
git push origin main
```

The revert restores i64-uniform emit. Any fixture additions can
stay (they're additive). Plan doc stays as future reference.
