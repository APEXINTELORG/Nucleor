**Theme:** Linux/macOS bootstrap — same compiler, same runtime, same gate, three OSes

The v0.2.51 audit explicitly called out **positive findings** so
v0.3 doesn't re-litigate them:

- No Windows path-separator hardcoding outside path helpers
  (`path_separator`, `path_normalize` from v0.2.23 already
  handle both interchangeably).
- No CRT-only function calls in user-facing helpers
  (`_putenv_s` / `_mkdir` / `_findfirst` / `gmtime_s` all paired
  with POSIX equivalents).
- No `<windows.h>` types in public APIs (`HANDLE`, `DWORD` are
  internal-only).
- No CRLF assumptions (`str_lines` from v0.2.26 strips `\r`).
- No backslash assumptions (`path_normalize` handles both).

## v0.3 work plan (4 phases from the audit)

### Phase 1 — Bootstrap path

**Goal:** produce a working `bin/nucleor` ELF on Linux x86_64 and
a `bin/nucleor` Mach-O on macOS arm64, both built from the same
`compiler/nucleor_s1_compiler.nr` source as the existing
`bin/nucleor.exe`.

**Steps:**
1. Stand up a Linux box (Ubuntu 22.04 LTS recommended) with
   LLVM 18 + clang installed.
2. Cross-compile `bin/nucleor.exe` → bootstrap binary OR build a
   minimal staging compiler that can run on Linux (e.g. a Rust
   transpile via `rust_bridge`, or a one-time clang manual link
   from `target/nucleor_s1_compiler.ll` produced on Windows).
3. Use the staging binary to compile `nucleor_s1_compiler.nr` →
   ELF binary on Linux.
4. Run that ELF binary to recompile itself (the fixed-point
   check). Verify the second-pass IR matches the first-pass IR
   byte-for-byte (same invariant the Windows v0.2.x chain held
   across every promotion).

**Risk:** none currently identified. The runtime audit confirms
no platform-specific source changes are needed.

### Phase 2 — Launcher (DONE in v0.2.53)

**Goal:** the POSIX `./nuc` wrapper resolves `clang` cleanly on
Ubuntu, Debian, Fedora, Arch, Homebrew (Intel + Apple Silicon).

**Status: DONE in v0.2.53.** Verified before any v0.3 binary
ships so users on POSIX systems trying the wrapper today get
correct behavior.

**Shipped:**
1. ✅ `NUCLEOR_CLANG_PATH` check first (parity with `nuc.bat`).
2. ✅ Full 10-path resolution chain (the four canonical paths
   from this spec plus 6 more fallbacks for LLVM 17 backstop and
   Homebrew unversioned/versioned variants):
   - `/usr/lib/llvm-18/bin/clang` (Ubuntu / Debian llvm-18 pkg)
   - `/usr/lib/llvm-17/bin/clang` (LLVM 17 fallback)
   - `/usr/bin/clang-18` (apt versioned binary)
   - `/usr/bin/clang` (Fedora / Arch generic)
   - `/opt/homebrew/opt/llvm@18/bin/clang` (Homebrew Apple Silicon, versioned)
   - `/opt/homebrew/opt/llvm/bin/clang` (Homebrew Apple Silicon, default)
   - `/usr/local/opt/llvm@18/bin/clang` (Homebrew Intel, versioned)
   - `/usr/local/opt/llvm/bin/clang` (Homebrew Intel, default)
3. ✅ Fail-fast error path with per-platform install commands:
   - `sudo apt install clang-18` (Ubuntu / Debian)
   - `sudo dnf install clang` (Fedora)
   - `sudo pacman -S clang` (Arch / Manjaro)
   - `brew install llvm@18` (macOS)
   - Skips clang check for `help`, `--help`, `--version` so users
     can self-diagnose without LLVM installed.
4. ✅ Refreshed missing-binary error message — was stale, now
   points at this milestone tracker for the bootstrap path with
   three current workarounds (Wine / source bootstrap / Windows
   host).

### Phase 3 — Verify gate parity (CI scaffolding shipped v0.2.55)

**Goal:** `tools/verify.sh` runs 186/186 on Linux + macOS,
identical to Windows.

**Status (v0.2.55):** GitHub Actions CI scaffolding exists in
`.github/workflows/ci.yml` with three OS matrix jobs
(`verify-windows`, `verify-linux`, `verify-macos`). The Windows
runner is wired to fail PRs that break the gate. The Linux and
macOS runners install LLVM 18 via `apt`/`brew` respectively,
note the missing `bin/nucleor` binary as a warning, and
`continue-on-error: true` so they don't block PRs until v0.3
phase 1 ships the binaries. Once binaries land, removing those
two `continue-on-error: true` lines flips the gate from
"informational" to "blocking" — the only remaining CI work is
that one-line edit per OS.

**Steps:**
1. Ship `bin/nucleor` Linux + macOS binaries (Phase 1).
2. Remove `continue-on-error: true` from the two non-Windows
   jobs so they block PRs.
3. Investigate any regression — the runtime audit predicts none,
   but real OS testing surfaces things audits miss
   (filesystem case-sensitivity, signal handling, CRT-vs-glibc
   `errno` semantics).
3. Add Linux + macOS GitHub Actions runners to CI. The Windows
   gate stays implicit (dev workflow).

### Phase 4 — Release artifact

**Goal:** v0.3 ships three pre-built binaries OR shifts to
GitHub Releases tarballs.

**Open policy questions** (not technical blockers — kickoff
decision):

1. **Pre-built binary distribution policy.** Keep
   `bin/nucleor*` committed (current v0.2 pattern) — adds
   `bin/nucleor-linux-x86_64` and `bin/nucleor-macos-arm64`. OR
   shift to GitHub Releases with versioned tarballs and `bin/`
   in the repo becomes Windows-only legacy.
2. **Linux distro CI target.** Ubuntu 22.04 LTS (default
   assumption). Debian 12, Fedora 39, Arch all should work but
   differ in clang path detection.
3. **macOS arch matrix.** Apple Silicon arm64 only (matches
   current developer machine baseline), or arm64 + Intel x86_64?
4. **CI runner.** GitHub Actions free tier covers Ubuntu +
   macOS — enable both.

## Out of v0.3 (deferred to v0.4+)

These are intentionally not on the v0.3 path:

- WASM backend (RFC-0022 phase 4) — separate target, separate
  RFC sub-section.
- Cross-compilation (e.g. build Linux binary from Windows host) —
  v0.3 ships native bins per host; cross-build is v0.4+.
- ARM Linux (e.g. Raspberry Pi). x86_64 Linux is the canonical
  v0.3 Linux; ARM Linux ships with the v0.4 sysroot manager.
